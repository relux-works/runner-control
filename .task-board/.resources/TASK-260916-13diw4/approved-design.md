# Runner Control — универсальное приложение для macOS

Статус: проект поведения и интерфейса, не реализованная функциональность.

## Решение

Runner Control управляет зарегистрированными GitHub Actions runners на текущем Mac. Количество, организации, репозитории, имя компьютера и пути не зашиты в приложение. Управление локальными службами работает без входа в GitHub. Подключение GitHub отдельно добавляет подтверждённые online/busy/labels/group и ссылки.

Основной сценарий: открыть меню → увидеть раннер → включить или выключить. Второй сценарий: открыть «Раннеры и настройки…» → добавить существующий раннер, изучить ошибку, настроить запуск.

Удалённый runner из GitHub нельзя включить локальным переключателем. Он не попадает в управляемый список без локальной установки. Удалённое управление по SSH — отдельное возможное расширение, не обещание текущего дизайна.

## 1. Меню

Ширина около 400 pt; имя компьютера берётся из macOS. При большом списке в нативном приложении список ограничен по высоте и прокручивается. Вверху: Runner Control, «Этот Mac · N служб включено». Счётчик относится к локальным службам, не к доступности в GitHub.

Каждая строка:

- Имя раннера из регистрации, пользовательский псевдоним при наличии.
- Организация или owner/repository и сервер, если это GitHub Enterprise.
- Локальное состояние: выключен, запускается, включён, выключается, ошибка, требуется настройка.
- Отдельная подпись GitHub: занят / готов / не в сети / не подключён / данные устарели.
- Явная кнопка действия: «Включить» или «Выключить…». Во время операции — индикатор и блокировка повторного действия только для этой строки.
- Нажатие на название открывает подробности в основном окне.

Кнопки предпочтительнее переключателя: выключение может потребовать решения о прерывании задачи и не завершается мгновенно. В макете предусмотрен вариант с переключателями для сравнения.

Нижняя область: «Включить все», «Выключить все…», «Добавить раннер…», «Раннеры и настройки…». Массовые команды относятся только к добавленным управляемым раннерам. Ошибки показываются по строкам, а не скрываются за общим успехом. Обновления Sparkle и выход переносятся в настройки; не занимают основную панель.

Иконка меню: контурная молния, когда всё выключено; заполненная, когда хотя бы одна служба включена; маленький знак ошибки при проблеме. Доступное описание всегда текстовое. Состояние не передаётся только цветом.

## 2. Добавление существующего раннера

Пустое состояние: «Добавьте раннер на этом Mac», действия «Найти на Mac» и «Выбрать папку…». Учётная запись GitHub не обязательна.

Обнаружение ограниченное, без сканирования всего диска:

1. Каталог установок, которым управляет приложение: ~/Library/GitHubActions.
2. Известные manifest-файлы служб текущего пользователя в ~/Library/LaunchAgents, связанные с actions.runner.*.
3. Каталоги, ранее выбранные пользователем.
4. Любой иной каталог — через системный выбор папки.

Существующие ручные службы manual-service.plist и стандартные пользовательские службы GitHub распознаются отдельными адаптерами. Демоны другого пользователя, запуск через терминал и неизвестные supervisor-системы показываются как неподдерживаемое управление: без притворного переключателя и без попытки создать второй процесс.

Результат поиска — кандидаты с именем, scope, путём и состоянием проверки. Обнаружение не запускает ничего. Пользователь выбирает «Добавить»; приложение объясняет конкретные изменения, если для управления нужно создать службу. Импорт без изменения существующей службы не перерегистрирует runner.

Проверки: .runner можно прочитать; server/scope определены; бинарник и runsvc.sh существуют; путь и рабочий каталог не содержат пробелов; manifest соответствует реальному каталогу/label; runner ещё не добавлен; нет второго управляющего процесса. Не читать и не экспортировать .credentials для обнаружения. Не выполнять скрипты кандидата во время сканирования.

Путь с пробелами → «Нужно изменить расположение» с выбором новой папки. Никакого автоматического переноса работающего runner: это отдельная операция после остановки с возможностью восстановления. Иначе тот же setup-go дефект вернётся.

«Создать новый runner» в первой версии — пошаговая инструкция регистрации в GitHub и последующее добавление выбранной папки. Полная загрузка/регистрация через приложение — следующий этап с отдельными правами и краткоживущим registration token.

## 3. Окно «Раннеры и настройки»

Нативное окно около 760 × 540 pt, доступное также повторным открытием приложения. Разделы:

### Раннеры

Список и панель выбранного runner: имя/псевдоним, адрес регистрации, локальный каталог, рабочий каталог, архитектура, версия, способ управления. Действия: включить/выключить, открыть GitHub, показать каталог, открыть журнал, выбрать перемещённую папку, убрать из приложения.

Для org runner не перечислять статически якобы разрешённые репозитории. При наличии прав показывать группу и полученные из GitHub ограничения с датой обновления; иначе «Доступ к репозиториям настраивается в GitHub». Пригодность к конкретной job зависит также от labels и правил workflow; online не гарантирует, что она попадёт сюда.

### GitHub

Необязательные подключения по серверу и учётной записи; можно подключить несколько. Секреты в Keychain, в настройках только ссылки на записи. Не импортировать молча учётные данные gh.

Основной способ подключения — «Войти через GitHub»: зарегистрированный GitHub App Runner Control и OAuth Device Flow. Ручное создание и вставка PAT не входит в основной сценарий. Вход и установка GitHub App в организацию/аккаунт — разные шаги: после входа приложение проверяет установки и доступ, затем при необходимости открывает установку или запрос одобрения владельцем организации. Требуемые разрешения: для org runners — Self-hosted runners/read; для repository runners — Administration/read. Чтение job/repository details требует дополнительных прав и включается отдельно. Отсутствие прав не означает отсутствие runner.

Локальное включение/выключение не зависит от доступности API. Нет сети / 401 / 403 / rate limit → соответствующая подпись, время последнего успешного обновления и возможность переподключения.

### Основные

«Открывать Runner Control при входе» — отдельно от запуска CI. Для новых управляемых служб запуск раннера при входе выключен. При импорте существующей службы её политика сохраняется и явно показывается, а не молча меняется. Изменение этой политики — самостоятельное действие пользователя.

Обновления: версия приложения, «Проверить обновления», автоматическая проверка и загрузка. Выход/обновление приложения оставляет уже запущенные службы работать; подтверждение выхода не обещает остановить CI. Во время изменения службы обновление откладывается до завершения операции.

## 4. Два независимых источника состояния

| Источник | Что подтверждает | Чего не подтверждает |
|---|---|---|
| macOS service/process | Процесс запущен или остановлен, последние ошибки запуска | Готовность принимать jobs в GitHub |
| GitHub API | Online/offline, busy, registration ID, labels | Мгновенное состояние процесса, гарантированное отсутствие новой job после ответа |

Храним отдельно LocalState, RemoteState, OperationState и время наблюдения. Потеря сети не превращает локальную службу в выключенную. Отсутствие регистрации не скрывает запущенную службу и возможность её остановить. При противоречии показываем оба факта, например «Служба выключена · GitHub: данные обновляются».

Локальное наблюдение: раз в 3 секунды при открытом меню, реже в фоне; немедленно после команды и пробуждения Mac. GitHub: объединённые запросы по scope, ориентировочно раз в 30 секунд при открытом меню с backoff и учётом rate limit. Старше 60 секунд — явно «данные устарели»; устаревшее busy=false не считается доказательством свободного runner.

## 5. Выключение

- Если GitHub сообщает busy: диалог «На раннере выполняется задача», действия «Оставить включённым» и «Прервать и выключить». Название/ссылка задачи — только если действительно получены из API.
- Если busy неизвестен, данные устарели или GitHub не подключён: «Занятость неизвестна. Выключение может прервать задачу».
- Даже свежий idle не исключает гонку с выдачей новой задачи. Поэтому первая универсальная версия всегда подтверждает остановку работающей службы.
- Остановку выполняет только адаптер известного runner; без kill по одному имени процесса и без воздействия на чужие службы.
- Успех — после подтверждения остановки. При таймауте — «Не удалось подтвердить остановку», повторная проверка, журнал. Не рисовать выключенное состояние заранее.

«Выключить после задачи» не включать в первую версию. Простое ожидание busy=false не запрещает GitHub выдать новую задачу. Нужен отдельно подтверждённый механизм прекращения приёма новых jobs; периодический опрос API сам по себе такой гарантии не даёт.

«Убрать из приложения» удаляет только запись каталога; предупреждает, если служба продолжит работать. Не удаляет файлы, регистрацию GitHub или сертификаты. Удаление runner из GitHub — отдельный будущий сценарий.

## 6. Архитектура и хранение

Сохранить Relux: UI Page → Container → Effect/Flow → actors/services → Action/Reducer → State. Sparkle и AppKit остаются адаптерами платформы.

- RunnerCatalog: versioned persistence, локальный UUID, canonical directory + bookmark, display override, controller kind, preferences. Переименование на GitHub не меняет локальную identity.
- RunnerDiscovery: ищет кандидатов в разрешённых местах; результат никогда не даёт автоматического разрешения на запуск.
- RegistrationReader: читает нужные поля .runner; сохраняет server URL, scope, remote agent ID. Не полагается на формат service label для определения организации.
- RunnerController protocol: inspect/start/stop/capabilities. Адаптеры для управляемой ручной службы и стандартного пользовательского LaunchAgent; unsupported — только чтение. Проверять конфигурацию повторно непосредственно перед действием.
- GitHubObserver: отдельно сопоставляет local registration и API runner по server + scope + remote ID, не по имени. При неоднозначности не прикрепляет случайный runner.
- CredentialStore: Keychain references, secret values не входят в Relux state и diagnostic exports.
- Diagnostics: ограниченный хвост логов с очисткой токенов; каталог _diag и фактические stdout/stderr пути из manifest, без зашитого Library/Logs имени.

Каталог хранится в Application Support/RunnerControl; это допустимо для настроек приложения. Установки и рабочие каталоги runners — в путях без пробелов. JSON не содержит секретов.

## 7. Миграция текущей установки

Однократно найти существующие macbook-iv и cocoaskills через общий discovery. Сохранить обнаруженные реальные каталоги, scope и service label. Не останавливать, не переименовывать, не перерегистрировать и не менять автозапуск. После успешной записи каталога удалить фиксированный список из Definition.installed(). Имя Mac и все строки интерфейса получать динамически.

Если импорт не удался, показать найденную установку с конкретной ошибкой и выбором папки. Не заменять её фиктивным runner и не удалять старые файлы.

## 8. Критерии готовности реализации

1. Чистый Mac показывает понятное пустое состояние; кнопки не подразумевают наличие Relux Works.
2. Можно добавить произвольный org/repo runner из нестандартного каталога без пересборки приложения.
3. Два одинаковых имени на разных scopes остаются двумя разными runners; один каталог нельзя импортировать дважды через symlink.
4. Без GitHub токена доступно локальное управление; busy честно неизвестен.
5. 401/403/offline и устаревшие данные не включают/выключают службы и не скрывают локальное состояние.
6. Повторный клик не создаёт дублирующий процесс; ошибка одной строки не блокирует весь список.
7. Удалённая .runner не мешает остановить уже известную работающую службу; неверный manifest блокирует запуск.
8. Массовая остановка показывает конкретный список и частичные ошибки.
9. Импорт не меняет действующие службы и политику входа; перезапуск приложения не включает CI.
10. Проверки выполняются unit/integration tests с временными безвредными службами; UI проверяется вручную, без UI-тестов согласно запросу.

## 9. Вход через GitHub API — уточнение дизайна

### Пользовательский сценарий

1. В настройках нажать «Войти через GitHub». По умолчанию github.com; Enterprise — отдельное подключение к явно выбранному серверу.
2. Приложение получает временный код через API и показывает его крупно: «Подтвердите подключение на GitHub». Кнопки «Скопировать код», «Открыть GitHub», «Отмена». Браузер — системный браузер пользователя; если Brave выбран по умолчанию, открывается Brave.
3. Пользователь вводит код и подтверждает Runner Control на странице GitHub. Пароль и 2FA вводятся только на сайте GitHub.
4. Приложение получает токены через API, проверяет профиль и показывает «Подключено как @username».
5. Отдельно показывает доступные установки GitHub App и репозитории. Если нужной организации нет — «Предоставить доступ организации…» / «Запросить одобрение». Не обещать, что простой вход автоматически открывает все организации пользователя.
6. После предоставления доступа состояния локальных runners дополняются сведениями GitHub. Runner из GitHub без соответствующей локальной установки остаётся информационной записью без кнопок запуска.

### Техническое решение

GitHub App с включённым Device Flow и истекающими user access tokens. В распространяемом macOS-приложении находится только публичный client_id. Client secret и private key GitHub App не включаются в бинарник, ресурсы, Sparkle-архив или исходники. Device Flow позволяет получить user access token без client secret; обновление токена, полученного через Device Flow, также не требует client secret по текущей документации GitHub. Отдельный сервер для этого сценария не нужен.

- POST /login/device/code: запрос к выбранному GitHub server.
- POST /login/oauth/access_token: опрос с выданным interval, учёт slow_down и expires_in.
- GET /user: подтверждение учётной записи.
- GET /user/installations и /user/installations/{installation_id}/repositories: доступные установки и ресурсы.
- REST runners/groups endpoints: наблюдение в рамках прав пользователя и установки.

Не использовать широкие OAuth scopes admin:org/repo как скрытую замену недостающим GitHub App permissions. Для регистрации новых runners позже потребуется явное повышение разрешений: Self-hosted runners/write для организации либо Administration/write для репозитория, а также соответствующие права пользователя. Эти права не требуются для локального переключателя.

GitHub App нужно один раз зарегистрировать как продукт Relux Works, разрешив установку другим аккаунтам. Каждая организация отдельно управляет установкой и доступом. Для GitHub Enterprise Server нельзя молча использовать client_id от github.com: требуется регистрация App на этом сервере и проверка поддержки Device Flow его версией. Пока она не настроена, локальное управление работает, подключение API показывает конкретное ограничение.

### Состояния авторизации

Не подключён → получаем код → ждём подтверждения → проверяем аккаунт → проверяем установки → подключён.

Отдельные исходы: пользователь отказал; отменено; код истёк (кнопка «Получить новый»); сеть недоступна (повтор с backoff); требуется установка App; требуется одобрение организации; требуется SSO; сессия отозвана (повторный вход). Отмена уничтожает временный device_code и прекращает опрос. HTTP 200 при device flow ещё не означает успех — проверяется тело ответа.

Access/refresh tokens хранятся в Keychain отдельно для server + user ID + app client ID. Refresh выполняет один actor, без конкурирующих обновлений; новая пара сохраняется атомарно. Сроки берутся из ответа API. При истечении refresh token или отзыве авторизации предлагается вход заново. Токены не попадают в Relux state, UI-логи, crash breadcrumbs или диагностические архивы.

«Выйти на этом Mac» удаляет локальные токены и останавливает опрос GitHub, оставляя локальные службы работать. «Отозвать доступ в GitHub…» открывает страницу управления авторизацией. Не выдавать локальный выход за глобальный отзыв или удаление установки App.

### Дополнительные критерии готовности

- Новый пользователь подключает GitHub без ручного создания PAT.
- Пользователь видит, под каким аккаунтом и к какому серверу выполнен вход.
- Вход без установки App заканчивается понятным шагом предоставления доступа, а не пустым списком.
- Отмена, истечение кода и slow_down проверены unit-тестами транспорта с подменяемыми часами.
- Refresh не дублируется при одновременных API-запросах; logout отменяет фоновые операции.
- Отсутствие сети и 403 не препятствуют включению/выключению уже добавленного локального runner.
